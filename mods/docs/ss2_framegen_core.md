# ss2 코어 프레임 생성(120Hz) — 앱이 알아야 할 계약

작성: 「커스텀 apk」방 (ss2-sp-core / emu-ex-plus-alpha / CustumApKS 담당), 2026-10-09.
코어: `rmdkdkr-png/ss2-sp-core` **main** ee87648 (framegen 가지 fast-forward 병합, svc-core 는 그대로).
바이너리: `cores/mednafen_ngp_libretro.android-arm64-v8a.so` (스탬프 a8499f6).

## 무엇을 하나
60fps 게임의 두 실제 프레임 사이에 중간 프레임을 끼워 120Hz 로 내보낸다. 픽셀을 섞지 않고
K2GE 스프라이트표·스크롤 레지스터를 보간해 같은 타일을 다시 그린다. 기본 「예측」방식은
상태를 저장한 채 다음 프레임을 미리 돌려 현재↔다음 중간을 그리고 되돌리므로 추가 지연 0.

## 코어 옵션
| 키 | 값 | 기본 |
|---|---|---|
| `ngp_framegen` | `auto` / `disabled` / `enabled` / `60` | `auto` |
| `ngp_framegen_idle` | `off` / `draw` | `off` |
| `ngp_framegen_mode` | `predict` / `interp` | `predict` |
| `ngp_flash_reduce` | `off` / `half` / `strong` | `off` (앱이 처음 한 번 «약하게»=`half`) |

`auto` 는 `RETRO_ENVIRONMENT_GET_TARGET_REFRESH_RATE` 가 60.25 의 짝수 배(120·240)일 때만 120 출력을 켜고, 아니면
60Hz 사이 그림(아래 15번)으로 간다. `60` 은 목표가 120 이어도 120 출력을 안 켠다(사이 그림만).
PocketCore feat/framegen-art dcb08a8 이 이 질문에 실측 패널 주사율로 답하므로 그대로 맞물린다.

## 프론트엔드가 보게 되는 것
1. **fps 선언**: 켜지면 `retro_get_system_av_info().timing.fps = 120.5` (60.25×2). 목표 주사율이
   로드 때 이미 120 이면 `retro_load_game` 안에서 바로 정해져 재초기화가 없다. 런타임에 바뀌면
   30 실제 프레임 뒤 `RETRO_ENVIRONMENT_SET_SYSTEM_AV_INFO` 로 알린다 (native.c 가 g_av 를 갱신하는 것 확인).
2. **호출 교대**: `retro_run` 짝수 = 실제 에뮬 프레임, 홀수 = 합성 프레임. 비디오는 매 호출 나간다.
3. **오디오**: 실제 프레임의 샘플(약 732)을 반씩 두 호출에 나눠 보낸다(호출당 약 366). 호출당
   샘플 수를 가정하지 않으면 그대로 된다.
4. **호출 속도 감시**: 100ms 넘는 공백을 뺀 1초 창 호출 속도가 2초 연속 90/s 미만이면 코어가
   스스로 60.25 로 돌아가고 `RETRO_ENVIRONMENT_SET_MESSAGE` 로
   「화면이 120Hz 로 돌지 않습니다 — 프레임 생성을 껐습니다」를 보낸다. 패널이 60 에 묶였을 때
   뜨는 게 정상이며, 그 뒤엔 앱 보간이 대신 맡으면 된다(앱은 vsync 실측으로 판단하니 자동).
   **차단은 영구가 아니다**(PR #1 지적 반영): 1·2·3 차 차단 뒤 10·20·40 초에 판정을 풀어
   `GET_TARGET_REFRESH_RATE` 를 다시 본다 — 아직 120 이면 30 실제 프레임 뒤 120.5 를 재선언한다
   (알림 「…껐습니다 (N초 뒤 다시 시도)」). 4 차 차단은 프레임 생성 옵션 **값이 바뀌거나** 게임을 다시 열
   때까지 유지(다른 옵션을 만져 GET_VARIABLE_UPDATE 가 와도 안 풀린다 — 80초짜리 주기가 재시작되지 않게).
   호출 속도 90/s 이상이 30 초 연속이면 횟수가 0 으로 돌아간다. PocketCore 처럼 실측 Hz 로 답하면 패널이 60 에
   머무는 동안엔 재시도해도 안 켜지고(횟수도 안 쓴다) 120 으로 돌아오면 살아난다. 앱은 코어가
   `SET_SYSTEM_AV_INFO` 로 120.5 를 다시 선언할 때 앱 보간을 다시 끄면 된다(이미 vsync 판정으로 자동).
   「켬」(강제)도 같은 차단·재시도를 따른다(안 그러면 60Hz 패널에서 2.5초마다 껐다 켰다 한다).
   코어 커밋: ss2-sp-core main 264841c (소스 05a1d16).
7. **스프라이트 일치 조건 (10/10, 실기 보고 「뉴트럴에서 프레임 깨짐」 수정)**: 사무쇼2는 체인 비트를 안 쓰고
   타일 번호는 슬롯마다 고유하지만, 포즈가 바뀔 때 **같은 타일 번호에 새 그림을 올려 쓴다**(롬 실측: 600프레임 중
   84프레임에서 935조각). 코어는 이제 속성어뿐 아니라 문자 RAM 의 타일 그림(16바이트)까지 같아야 「같은 조각」으로
   보고 움직인다 — 포즈 교대 프레임(약 8프레임마다 1장)은 base 포즈를 온전히 그리고 그 8ms 만 60Hz 와 같다.
   단독 스프라이트·체인 그룹(다른 게임용)은 슬롯별로 짝짓되, 같은 타일 번호를 둘 이상의 조각이 쓰면 그 조각들이 모두
   같은 벡터로 움직일 때만 믿는다(자리 바꿈이면 정지).
   체인 없는 메타스프라이트는 「우선순위·팔레트가 같고 16px 안에 붙는 연속 슬롯」을 한 캐릭터로 묶어 강체로 움직인다
   (PocketCore 방 ss2fg_consensus.patch 의 묶음 규칙). 무리 안에서는 조각을 **겉모습으로** 짝짓는다(PocketCore 방
   패치 3판 b38e05d 의 규칙을 main 에 들임) — 조각마다 다음 프레임 전체에서 플립·우선순위·팔레트·타일 그림이 같은
   조각을 슬롯·타일 번호와 상관없이 찾아 그 거리에 표를 던지고(짝이 여럿이면 표를 나누고 넷 초과·빈 조각은 기권),
   최빈 이동량으로 포즈가 바뀐 조각까지 함께 옮긴다. 1등에 표를 준 조각이 둘 이상, 1등이 2등(±1px 창 밖)의 두 배
   이상, 그림 있는 조각의 1/4 이상이어야 하고 아니면 그 무리는 그 프레임만 정지(과반 대신 「뚜렷한 1등」인 것은
   같은 그림이 줄지어 선 효과의 대칭 표 때문). 벡터를 쓰기 전에 「자리+벡터」에 같은 그림·플립·팔레트·우선순위의
   조각이 있는 수를 제자리와 견주어 제자리가 같거나 많으면 쓰지 않는다(슬롯 번호 밀림의 가짜 -8px 방지, PocketCore 방
   c0e2f79 규칙). 롬 실측 600프레임(같은 OAM 덤프로 비교): 무리가 선 프레임 100 → 26, 움직인 조각 +17%, 잃음 0.
   체인을 쓰는 게임용 그룹 강체도 있다(사무쇼2엔 해당 없음).
8. **4배 — 게임 박자 맞춤 (10/10, PocketCore 방 20_ss2fg_4x.patch 023a638 을 main 에 들임)**: 사무쇼2는 스프라이트를
   짝수 프레임에만, 배경 스크롤을 홀수 프레임에만 움직인다(초당 30번씩. 롬 실측 600프레임: 스프라이트 자리 바뀐 224장이
   전부 한 홀짝, 배경 바뀐 25장 중 23장 반대 홀짝). 2배는 새 그림 사이 빈칸 셋 중 하나만 채웠다. 예측 방식에서 코어 옵션
   `ngp_framegen_mult`=4(기본)이면 실제 N 직후 N+1·N+2 를 미리 돌려 스프라이트·스크롤 각각 «다음 바뀌는 프레임 K»와
   «지난번 바뀐 때 L»을 찾고 L~K 를 고르게 나눠 실제 호출(τ=N)과 합성 호출(τ=N+½) 두 장을 만든다 — 실제 호출의 그림도
   박자에 맞춰 옮긴다(«날것» 실제 프레임은 안 나온다; 입력이 바뀌면 다음 실제 변화에서 바로잡힘). 에뮬 계산 약 1.5배.
   `ngp_framegen_mult`=2 는 예전 2배. 보간 방식의 4배는 «반반»(PocketCore 방 f3bc9bf 을 main 에 들임): 화면을 반 프레임
   늦게 보여 주므로(지금 보간과 같은 +8ms) 다음 바뀌는 프레임이 늘 N 이나 N+1 — N+1 한 프레임만 미리 돌려 실제 호출에
   τ=N-½, 합성 호출에 τ=N. 계산은 예측 2배와 같다. 앱 설정 「배수」는 이 옵션으로 통한다.
